認証のしくみ — 2トークン方式を理解する

このサーバーの認証は「短命のアクセストークン(JWT)」と「長命のリフレッシュトークン」の2枚看板です。なぜ2つ必要なのか、パスワードはどう守られているのか、src/services/authService.ts と src/lib/ を軸に読み解きます。

3-1全体像 — なぜトークンが2種類あるのか

ログインに成功すると、サーバーは2種類のトークンを返します。

アクセストークン(JWT)

  • 有効期限 15分(短命)
  • 毎リクエストの Authorization: Bearer ヘッダーに載せる
  • 検証は署名チェックのみ、DB 参照なし(高速)
  • サーバーには保存されない

リフレッシュトークン

  • 有効期限 30日(長命)
  • アクセストークンの期限が切れたときだけ /auth/refresh に送る
  • ハッシュが DB に保存され、照合される
  • 1回使うと新しいものに交換される(ローテーション)

2つに分ける理由は、「安全性」と「速度・利便性」のトレードオフを両取りするためです。

  • アクセストークンを短命にする → 盗まれても最長15分で無効になる。しかも検証に DB を見ないので毎リクエストが高速。
  • リフレッシュトークンを長命にする → ユーザーは30日間ログインし直さなくてよい。こちらは DB で管理されるので、ログアウトや不正検知でサーバー側から即座に無効化できる。
もし1種類だったら: 長命の JWT 1枚だと、盗まれたとき30日間止める手段がない(JWT はサーバーに保存されないため)。短命の JWT 1枚だと15分ごとに再ログインが必要でアプリとして使い物にならない。毎回 DB でセッションを引く方式(古典的なセッション認証)は無効化が簡単な代わりに毎リクエスト DB アクセスが発生する。2トークン方式はこれらの弱点を組み合わせで消した、モバイル API の定番構成です。

3-2JWT — 中身と検証のしくみ

JWT とは?

JWT(JSON Web Token、「ジョット」)は「ヘッダー.ペイロード.署名」の3パートをドットで繋いだ文字列。ペイロードには userId や有効期限 exp が JSON で入っており、誰でも読めます(Base64 エンコードされているだけ)。安全性は最後の署名が担保します。署名はサーバーだけが知る秘密鍵(JWT_SECRET)から計算されるため、ペイロードを1文字でも改ざんすると署名が合わなくなり検証で弾かれます。「読めるが偽造できない身分証」と覚えてください。

クレーム意味このコードでの役割
userId独自クレーム「誰のトークンか」。auth ミドルウェアがここから本人 ID を得る
iatissued at(発行時刻)いつ発行されたか
expexpiration(失効時刻)検証時に自動チェックされる。これが「15分」の正体
jtiJWT ID(トークン固有 ID)ランダム値。同じ秒に発行しても毎回違うトークンになる

検証側(verifyToken)は署名と exp を確認するだけで、DB には一切アクセスしません。これが第2章で見た auth ミドルウェアの「DB を参照しない」設計の根拠です。失効管理はリフレッシュトークン側に寄せてあるので、仮に古い端末のアクセストークンが生き残っていても最長15分で自然に死にます。

3-3パスワードの守り方 — Argon2id

パスワードは絶対に平文(そのままの文字列)で保存しません。DB に入るのは Argon2id という一方向関数を通した「ハッシュ」で、ここから元のパスワードは復元できません。ログイン時は入力パスワードを同じ関数に通し、結果が一致するかで照合します。

なぜ SHA-256 ではなく Argon2id?(ソルトとは?)

SHA-256 のような高速ハッシュは、攻撃者も高速に総当たりできてしまいます(GPU で毎秒数十億回)。Argon2id は意図的に計算を重く・メモリ食いにした「パスワード専用」ハッシュで、OWASP(Web セキュリティの標準団体)の第一推奨です。ソルトはハッシュ計算に混ぜるランダム値で、同じパスワードでも毎回違うハッシュになるようにするもの。「よくあるパスワードのハッシュ一覧表(レインボーテーブル)」との照合攻撃を無効化します。Argon2 はソルトを自動生成してハッシュ文字列に埋め込むため、コードでソルトを管理する必要がありません。

3-4リフレッシュトークン — 高エントロピー乱数 + ハッシュ保存

2つの重要な設計判断が詰まっています:

  • DB にはハッシュだけを保存する。 万一 DB が流出しても、攻撃者はハッシュからトークン本体を復元できず、なりすましできません。
  • こちらは SHA-256 でよい。 パスワードと違い 48 バイトの完全ランダム値(高エントロピー)なので総当たりが物理的に不可能。重い Argon2 を使う必要がなく、毎リクエスト高速に照合できます。「何をどのハッシュで守るか」の使い分けは業務でそのまま役立つ知識です。

DB 側の置き場所は users テーブルの2列(refresh_token_hash, refresh_token_expires_at)です(prisma/schema.prisma)。

3-54つのエンドポイントの流れ

認証の全処理は src/services/authService.ts にあり、心臓部は共通関数 issueSession() です。

register / login — 入口

register入力検証(Zod) → メール重複チェック(あれば 409 CONFLICT) → パスワードを Argon2id でハッシュ化して INSERT → issueSession(登録と同時に自動ログイン)
↓ どちらも最後は同じ
login入力検証 → メールでユーザー検索 → verifyPassword で照合(失敗なら 401) → issueSession
細部に注目: login の失敗メッセージは「メールアドレスまたはパスワードが正しくありません」で統一されています。「メールが存在しない」と「パスワードが違う」を区別して返すと、攻撃者に「このメールは登録済み」という情報を与えてしまうため(ユーザー列挙攻撃対策)、わざと曖昧にするのが定石です。

refresh — トークンの交換とローテーション

ポイントは最後の issueSession()。新しいリフレッシュトークンのハッシュで DB を上書きするため、いま使ったトークンはこの瞬間に無効になります。これをリフレッシュトークンローテーションと呼びます。トークンが盗まれてどこかで使われると、正規ユーザー側のトークンが突然効かなくなるので、盗難の検知にもつながります。

logout — サーバー側の破棄

updateRefreshToken(userId, null, null) で DB のハッシュを消すだけ。以後そのリフレッシュトークンは使えません。手元のアクセストークンは残りますが、最長15分で失効します。

3-6「後勝ち方式」 — 1ユーザー1セッション

users テーブルにはリフレッシュトークンの列が1組しかないため、別の端末でログインすると前の端末のトークンは上書きされて無効になります。最後にログインした端末だけが有効 — これが後勝ち方式です。

このプロジェクト(後勝ち)複数端末対応する場合
テーブル設計users にトークン列を直接持つrefresh_tokens を別テーブルに分離し、1ユーザー N 行
実装の複雑さシンプル端末管理・掃除(期限切れ行の削除)が必要
ユーザー体験別端末でログインすると前の端末はログアウトされる複数端末で同時ログイン可

開発中に「さっきの token が急に 401 になった」と感じたら、大抵は別ターミナル・別端末で再ログインして前のトークンが上書きされたのが原因です(よくある詰まりポイント)。

3-7クライアント(Flutter)から見た使い方

1. ログイン成功token と refreshToken を受け取り、端末の安全な保存領域(Keychain / Keystore)へ
↓
2. 通常のリクエスト毎回 Authorization: Bearer <token> と Api-Version: 1 を付ける
↓ 15分経過して 401 が返ってきたら
3. 自動リフレッシュPOST /auth/refresh に refreshToken を送る → 新しい2トークンに差し替えて、失敗したリクエストを再送(ユーザーは何も気づかない)
↓ refresh も 401 なら(30日放置 or 別端末ログイン)
4. ログイン画面へ再ログインしてもらう

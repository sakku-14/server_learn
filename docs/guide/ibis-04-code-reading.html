4-1題材① GET /users/me — 最小構成の縦断読み

「認証中ユーザー自身のプロフィールを返す」だけのエンドポイント。4層すべてを最短距離で通るので、最初に読むのに最適です。

ROUTEsrc/routes/userRoutes.ts

ルート層のファイルは長く見えますが、実体は「仕様の宣言」です。createRoute で書いた内容(パス・入出力の形・エラー)はそのまま OpenAPI 仕様書になり、/reference に自動反映されます。仕様書を別ファイルで手書きしないコードファースト方式なので、実装と仕様が絶対にズレません。

OpenAPI / Scalar とは?

OpenAPI は REST API の仕様を記述する業界標準フォーマット(旧称 Swagger)。「どんなエンドポイントがあり、何を受け取り何を返すか」を機械可読な JSON で表します(このサーバーでは /doc で配信)。Scalar はその JSON を人間向けの綺麗な画面にして /reference で表示する UI ライブラリです。アプリ開発者(Flutter 側)との「仕様のすり合わせ」はこの画面を見ながら行えます。

なお app.ts 側の app.route('/users', userRoutes) により、ここでの path: '/me' は実際には /users/me になります(プレフィックスの合成)。

CONTROLLERsrc/controllers/userController.ts

たった3行。Controller の仕事は「Context から入力を取り出す → Service を呼ぶ → 結果を HTTP レスポンスにする」だけで、判断ロジックを一切持ちません。この薄さが正常で、Controller が太り始めたら設計が崩れているサインです。

Context<AppEnv> の型は何をしている?

c.get('user') や c.get('logger') のような「Context に載せた値」は、そのままだと型が分かりません。src/types.ts の AppEnv インターフェイスで「Context には requestId: string、logger: Logger、user: { id: number } が入る」と宣言し、Context<AppEnv> と型引数(ジェネリクス)で渡すことで、c.get('user') の戻り値に正しい型が付き、タイポはコンパイルエラーになります。TypeScript プロジェクトの型安全を支える典型パターンです。

SERVICEsrc/services/userService.ts

★の行が地味に重要です。Repository が返す user には password(ハッシュ)や refreshTokenHash も含まれていますが、返すフィールドを明示的に選んで詰め直すことで秘密情報の漏出を防いでいます。return user と横着すると事故になる、バックエンドの頻出ポイントです。

REPOSITORYsrc/repositories/userRepository.ts

Repository は Prisma 呼び出しの薄いラッパーです。「わざわざ層を挟む意味あるの?」と思うかもしれませんが、(1) テストでこの層だけ偽物に差し替えられる、(2) 「DB アクセスは全部ここ」と場所が確定する、(3) 将来クエリが複雑化しても影響がこの層で止まる、という利点のための投資です。

DBprisma/schema.prisma

@map は「TypeScript ではキャメルケース(refreshTokenHash)、DB ではスネークケース(refresh_token_hash)」という両者の命名規約を橋渡しする指定です。このファイルを変更したらマイグレーションで DB に反映します(手順は第5章)。

4-2題材② POST /auth/register — 入力があるパターン

今度は「クライアントから JSON ボディを受け取る」エンドポイント。追加で登場するのは入力検証(バリデーション)です。

SERVICEZod スキーマと validate()

引数が input: unknown になっているのに注目してください。「外から来たデータは何が入っているか分からない」という前提を型で表現し、validate() を通って初めて { name, email, password } という信頼できる型になります。境界で検証し、内側は信頼する——バックエンドの基本原則です。

Zod とは? 宣言的バリデーションの利点

Zod は「データの形」をコードで宣言するライブラリ。z.string().email() のようにルールを繋げて書きます。利点は (1) 検証ロジックの if 文の山を書かなくてよい、(2) スキーマから TypeScript の型を自動で導ける(z.infer)、(3) このプロジェクトでは OpenAPI 仕様書の生成にも同じスキーマを使い回せる、の3点。1つの定義が「検証・型・仕様書」の3役を兼ねる、このプロジェクトの背骨です。

エラーの一貫性: validate()(src/lib/validation.ts)は Zod の失敗を { code: 'VALIDATION_ERROR', detail: { email: 'メールアドレスの形式が…' } } というフィールド名 → メッセージの形に変換します。ルート層の createOpenAPIApp()(src/lib/openapi.ts)の defaultHook も同じ変換を使うため、どこで検証に落ちてもアプリ側は同じ形式のエラーを受け取れます。アプリはこれをそのままフォームのエラーメッセージ表示に使えます。

4-3支える部品たち — lib/ と config/

本流の4層を支える「道具箱」も、役割さえ掴めば怖くありません。

ファイル役割詳しくは
lib/prisma.tsPrismaClient を1個だけ生成して全体で共有(接続の使い回し)—
lib/errors.tsAppError と unauthorized() 等のヘルパー第2章
lib/validation.tsZod 検証 → VALIDATION_ERROR 変換本章 4-2
lib/jwt.ts / lib/password.ts / lib/refreshToken.tsトークン・パスワードの暗号まわり第3章
lib/openapi.tsルート定義の共通部品(エラー形式・Api-Version ヘッダー・Bearer 認証の宣言)本章 4-1
lib/logger.tsPino ロガー。開発時は色付き表示 + 日次ファイル、本番は JSON を標準出力へ第2章
config/env.ts環境変数を起動時に Zod で検証。本番で弱い JWT_SECRET なら起動拒否—
config/env.ts の fail-fast 思想: 設定ミスは「動き出してから変なエラー」になると原因究明が大変です。起動の瞬間に全環境変数を検証して、ダメなら理由を表示して即終了(process.exit(1))。壊れているなら早く・大きな音で壊れろという運用の知恵で、業務でも必ず見る形です。

4-4テストコードの読み方

モック(vi.mock)とは?

モックは本物の代わりに使う「偽物の部品」。vi.mock('../repositories/userRepository.js') と書くと、テスト中は Repository の全関数が偽物になり、mockResolvedValue(...) で「この関数はこの値を返すことにする」と台本を与えられます。DB なしで「ユーザーが存在しない場合」「重複している場合」など任意の状況を再現できるのが強みです。

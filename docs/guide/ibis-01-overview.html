ibis backend を読み解く — 第1章(全5章)

全体像 — このサーバーは何者で、どう動いているのか

Flutter アプリ「ibis」の裏側で動くバックエンド API を、マクロ(全体の地図)からミクロ(1行のコード)へ順に読み解くシリーズです。第1章では、技術スタック・アーキテクチャ・ディレクトリ構成という「地図」を頭に入れます。

1-1このサーバーの役割

このプロジェクト(server/)は、スマホアプリ向けの バックエンド API サーバー です。アプリ(Flutter)は画面を描くだけで、「ユーザー登録」「ログイン」「プロフィール取得」といったデータの処理はすべて HTTP でこのサーバーに依頼します。サーバーは処理結果を JSON で返します。

API / エンドポイントとは?

API(Application Programming Interface)は「プログラム同士の窓口」の総称。この文脈では「HTTP でリクエストを受けて JSON を返すサーバー」を指します。エンドポイントはその窓口の1つ1つで、「HTTP メソッド + URL パス」の組で表します(例: POST /auth/login)。業務では「ログインのエンドポイント叩いて」のように使います。

現在このサーバーが持つエンドポイントは次の通りです。

エンドポイント役割認証
POST /auth/register新規登録(登録と同時に自動ログイン)不要
POST /auth/loginログイン。トークンを発行不要
POST /auth/refreshトークンの再発行(第3章)不要*
POST /auth/logoutログアウト。サーバー側のトークンを破棄必要
GET /users/me自分のプロフィール取得必要
DELETE /users/me退会(ユーザー削除)必要
GET /health ・ /health/ready死活監視(ヘルスチェック)不要
GET /reference ・ /docAPI 仕様書(自動生成、ブラウザで見る)不要

* refresh は JWT の代わりにリフレッシュトークン自体が本人確認の材料になります(第3章)。

「スタック」とは、そのプロジェクトが積み上げている技術の組み合わせのこと。面接や業務会話で「Hono + Prisma + PostgreSQL 構成です」のように一言で説明できると強いです。

ORM とは?

ORM(Object-Relational Mapping)は、DB のテーブルをプログラムのオブジェクトに対応付けるライブラリ。SELECT * FROM users WHERE id = 1 という SQL の代わりに prisma.user.findUnique({ where: { id: 1 } }) と書けます。利点は (1) 型が付く(存在しない列名を書くとコンパイルエラー)、(2) SQL インジェクションを防ぎやすい、の2つです。

フレームワークとライブラリの違いは?

どちらも「他人が書いた再利用可能なコード」ですが、ライブラリは自分のコードから呼び出すもの(Zod など)、フレームワークは逆に自分のコードが呼び出される「骨組み」を提供するもの(Hono)。Hono がリクエストを受けて、登録しておいた自分の関数を呼んでくれます。

1-3リクエストの旅 — マクロの地図

アプリが GET /users/me を送ってからレスポンスが返るまで、リクエストは次の駅を順番に通ります。この図がシリーズ全体の地図です。第2章以降で各駅を拡大していきます。

Client
Flutter アプリHTTP リクエストを送る(ヘッダーに認証トークンを添付)
↓ HTTP (JSON)
Middleware
ミドルウェア群 …第2章全リクエスト共通の関所。セキュリティヘッダー / CORS / ログ / レート制限 / API バージョン / 認証(JWT 検証)
↓
Route
ルート層 src/routes/URL とメソッドを見て担当 Controller へ振り分ける。入出力の形(スキーマ)もここで宣言 → API 仕様書が自動生成される
↓
Controller
コントローラ層 src/controllers/リクエストから入力を取り出し、Service を呼び、結果を HTTP レスポンスに変換する「交通整理」役。判断はしない
↓
Service
サービス層 src/services/ビジネスロジックの本体。入力検証、重複チェック、トークン発行などの「判断」はすべてここ
↓
Repository
リポジトリ層 src/repositories/DB の読み書き「だけ」を担当。Prisma の呼び出しをまとめる
↓ SQL (Prisma が生成)
DB
PostgreSQLDocker コンテナで稼働。データの永続化

レスポンスは同じ道を逆向きに戻ります。途中でエラーが起きた場合は、どの層からでも例外を投げれば共通のエラーハンドラーが統一形式の JSON に変換します(第2章)。

1-4レイヤードアーキテクチャ — なぜ層に分けるのか

上の図のように役割ごとに層を分ける設計をレイヤードアーキテクチャと呼びます。業務のバックエンド開発では最も標準的な構成です。分ける理由は主に3つ:

理由具体例
変更に強い「DB を PostgreSQL から別の DB に変える」なら Repository 層だけ、「レスポンスの形を変える」なら Controller/Route 層だけ直せばよい
テストしやすいService 層のテストでは Repository を偽物(モック)に差し替え、DB なしでロジックだけを高速に検証できる(第5章)
迷子にならない「入力チェックのバグ → Service」「SQL が遅い → Repository」のように、直す場所が機械的に決まる
覚え方: 依存は常に外側 → 内側の一方向(Route → Controller → Service → Repository)。内側の層は外側を知らない(Service は HTTP のことを知らないので、どの窓口からでも再利用できる)。これが崩れると層を分けた意味がなくなります。

環境変数 / .env とは?

環境変数は、コードの外から渡す設定値。DB の接続先(DATABASE_URL)や署名用の秘密鍵(JWT_SECRET)のように「環境ごとに違う値」「秘密にすべき値」をコードに埋め込まず外出しします。.env ファイルはローカル開発用の環境変数置き場で、秘密情報を含むため git にコミットしません(.gitignore 済み)。このプロジェクトは src/config/env.ts が起動時に Zod で検証し、設定漏れがあれば即座に終了します(fail-fast)。

1-6起動の流れ — index.ts と app.ts

プログラムの入口(エントリーポイント)は src/index.ts です。わずか 28 行で、やることは「app.ts で組み立てたアプリを、ポート 3000 で待ち受けさせる」だけ。

グレースフルシャットダウンとは?

サーバーを止めるとき、処理中のリクエストを完了させてから終了する作法。デプロイやスケールイン(サーバー台数を減らすこと)の際、基盤(Cloud Run や k8s)は SIGTERM というシグナルを送ってきます。これを無視して即死すると、その瞬間に処理中だったユーザーにエラーが返ってしまう。server.close() で新規受付を止めて待ち、保険として10秒で強制終了する実装になっています。

一方 src/app.ts はアプリの組み立て図です。ミドルウェアの適用順、ルートの登録、エラーハンドラーの設定がすべてここに書かれており、迷ったらまず app.ts を読むのがこのプロジェクトの読み方です。詳細は第2章で1行ずつ追います。

1-7開発環境の動かし方

開発時の全体像はこうなっています: アプリ本体は tsx watch(ファイル保存で自動再起動)でローカル実行、DB だけ Docker で動かします。

コマンドやること
make up初回セットアップ込みの一発起動。DB 起動 → マイグレーション適用 → 初回ならシード投入 → 開発サーバー起動
make downDB コンテナ停止(データは保持)
make testDB を起動してからテスト実行
make studioPrisma Studio(DB の中身を GUI で見るツール)
make migrateスキーマ変更を DB に反映(第5章)

起動後にブラウザで http://localhost:3000/reference を開くと、コードから自動生成された API 仕様書(Scalar UI)が見られます。このページからそのままリクエストを試せるので、動作確認の起点として最初に覚えるべき URL です。

シード / マイグレーションとは?

マイグレーションは DB の構造変更(テーブルや列の追加)を SQL ファイルの履歴として管理・適用する仕組み。シード(seed)は開発用のテストデータを DB に投入すること(prisma/seed.ts)。どちらも「チームの誰の環境でも同じ DB 状態を再現する」ためにあります。

ミドルウェア — すべてのリクエストが通る関所

Route にたどり着く前に、リクエストは複数の「関所」を順番に通過します。この章では src/app.ts と src/middlewares/ を読み解き、各関所が何を守っているのかを理解します。

2-1ミドルウェアとは何か

ミドルウェアは「本処理(Controller)の前後に挟み込む共通処理」です。認証・ログ・レート制限のような処理は全エンドポイントで必要になるため、各 Controller に毎回書くのではなく、通り道に1回だけ設置します。

Hono のミドルウェアはこういう形をしています:

await next() を境に「行き」と「帰り」の処理が書けるのがポイント。玉ねぎのように処理が入れ子になるのでオニオンモデルとも呼ばれます。c は Context(コンテキスト)で、リクエスト・レスポンス・共有データ(c.set() / c.get())をまとめて持ち運ぶオブジェクトです。

2-2適用順序 — app.ts を上から読む

ミドルウェアは登録した順に実行されるため、app.ts の記述順そのものが設計です。

① secureHeaders()防御用 HTTP ヘッダーを全レスポンスに付与
↓
② cors(…)ブラウザからのアクセスを許可リスト方式で制御
↓
③ requestContextリクエスト ID の採番と、アクセスログの記録
↓ /health はここで応答して終了(以降の関所を通らない)
④ globalRateLimitIP ごとに毎分 100 回まで
↓ /auth・/users のルート内でさらに…
⑤ apiVersionApi-Version: 1 ヘッダーの検証(全ルート)
↓
⑥ auth / authRateLimitauth: JWT 検証(保護ルートのみ)/ authRateLimit: 認証系は毎分 10 回まで
↓
Route Controller の本処理へ
順序の意図: ヘルスチェック(/health)がレート制限より前にあるのは、監視システム(ロードバランサー等)が高頻度で叩いてもブロックされないため。逆に認証系の厳しいレート制限はルート側に置き、必要な窓口だけに効かせています。

2-3各ミドルウェアの中身

① secureHeaders — ブラウザ向けの基本防御

Hono 組み込み。X-Frame-Options(クリックジャッキング対策)など、セキュリティ系のレスポンスヘッダーをまとめて付けます。1行で「やらない理由がない」定番対策が入るので、業務でもほぼ必ず入れます。

② cors — どのサイトからのアクセスを許すか

CORS とは?

CORS(Cross-Origin Resource Sharing)は、ブラウザ上の JavaScript が「別のドメインの API」を呼ぶことを制御する仕組み。ブラウザは既定で別ドメインへのリクエストの結果を JavaScript に渡しません。サーバーが「このオリジン(ドメイン)なら OK」とヘッダーで宣言することで許可します。重要なのは、これはブラウザだけのルールだという点。Flutter のネイティブアプリや curl には CORS は関係ありません。ここで設定しているのは API 仕様書(/reference)などブラウザ経由のアクセスのためです。

③ requestContext — ログと「リクエストの背番号」

すべてのリクエストに UUID の背番号(requestId)を振り、その背番号入りのロガーを Context に載せます。以降どの層でログを書いても自動で requestId が付くので、大量のログの中から「あの1回のリクエストに関するログだけ」を抽出できます。障害調査(トラブルシュート)の生命線で、業務ではこの仕組みがないと運用になりません。

構造化ログとは?

ログを「人間向けの文章」ではなく JSON で出すこと。{"level":"info","requestId":"...","status":200,"responseTimeMs":12} のような形式なら、ログ収集基盤(Datadog、CloudWatch 等)で「status が 500 のログだけ」「応答が 1 秒超のログだけ」と機械的に検索・集計できます。このプロジェクトのロガー Pino は高速な構造化ログの定番です。開発中は pino-pretty で人間に読みやすく整形され、logs/YYYYMMDD.log にも日次ファイルとして保存されます(30日で自動削除)。

④ rateLimit — 使いすぎ・攻撃への防波堤

IP アドレス単位で1分あたりの回数を制限します。認証系だけ厳しいのは、パスワード総当たり攻撃(ブルートフォース)対策。毎分10回では総当たりが事実上不可能になります。超過すると 429 RATE_LIMITED が返ります。

業務での注意点(コードのコメントにも明記): ① IP の特定に X-Forwarded-For ヘッダーを使うため、本番では必ずリバースプロキシ/ロードバランサーの背後に置くこと(直接公開だと偽装可能)。② カウントはインメモリ(サーバーのメモリ上)なので、サーバーを複数台に増やす(スケールアウト)なら Redis 等の共有ストアに差し替えが必要。

⑤ apiVersion — アプリ世界特有のバージョン管理

全リクエストに Api-Version: 1 ヘッダーを必須にし、無い・非対応なら 400 を返します(src/middlewares/apiVersion.ts)。

なぜ API にバージョンが要るのか?

Web と違い、スマホアプリはユーザーが更新しない限り古いバイナリが動き続けます。API のレスポンス形式を変えると、古いアプリが壊れる。そこで「バージョン 1 の契約」を宣言させておき、互換性を壊す変更をするときは バージョン 2 を新設して両方をしばらく併存させます。最初からこのヘッダーを必須にしておくのは、モバイルバックエンドの定石です。

⑥ auth — JWT 検証(詳細は第3章)

トークンが正しければ c.set('user', …) で本人の ID を Context に載せ、Controller は c.get('user') で受け取ります。検証で DB を参照しないのがこの設計の特徴で、理由は第3章で説明します。

2-4エラーハンドラー — 例外の終着駅

ここまでの関所や、この先の Service で問題が起きたとき、コードは throw(例外を投げる)するだけです。投げられた例外はすべて app.onError(errorHandler) に集まります。

対になるのが src/lib/errors.ts の AppError。「ステータスコード + エラーコード + 詳細」を持つ自作の例外クラスで、unauthorized() notFound() のような生成ヘルパーが用意されています。

ヘルパーHTTPcode使う場面
validationError(detail)400VALIDATION_ERROR入力の形式が不正
unauthorized(msg)401UNAUTHORIZED未ログイン・トークン不正
notFound(msg)404NOT_FOUND対象データが存在しない
conflict(detail)409CONFLICTメールアドレス重複など
tooManyRequests()429RATE_LIMITEDレート制限超過
(自動)500INTERNAL_ERROR想定外のバグ・障害

この設計により、レスポンスのエラー形式は必ず { "code": "...", "detail": {...} } に統一されます。これを エラー契約 と呼び、アプリ側(Flutter)は code を見て「401 ならログイン画面へ」のような分岐を安心して書けます。

この設計の気持ちよさ: Service のコードは throw conflict({...}) と1行書くだけ。try/catch をあちこちに書かず、「エラーをどう HTTP に変換するか」は errorHandler が一手に引き受けます。関心の分離の好例です。

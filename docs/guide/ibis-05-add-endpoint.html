5-1鉄則 — 内側から外側へ

実装順は毎回同じです: DB(schema)→ Repository → Service → Controller → Route。呼ばれる側(内側)を先に作れば、外側を書くときには呼ぶ相手が常に存在し、「まだ無い関数を呼ぶ」宙ぶらりんな状態が生まれません。

どの層を触るかの見極め(設計チェックリスト):
・新しいデータを DB に保存する? → schema.prisma + マイグレーション
・DB を読み書きする? → Repository に関数追加
・入力を受け取る / 判断ロジックがある? → Service(Zod スキーマ + 処理)
・新しい URL が増える? → Controller + Route(createRoute)
・認証が必要? → 既存の auth ミドルウェアが付くルート群に置くだけ(/users 配下なら自動)

パターン別の触る範囲はこうなります:

やりたいことschemaRepositoryServiceController/Route
既存データを返すだけの GET—△(既存流用可)✅✅
既存レスポンスに項目を足す——✅(戻り値に追加)✅(スキーマに追加)
新しいデータを保存する(今回の phone)✅✅✅✅

5-29 STEP ウォークスルー

0

準備 — 環境とブランチ

ブランチ名は feat/内容(新機能)、fix/内容(バグ修正)が慣習です。

1

要件を言葉にする(コードを書かない)

「何を・誰が・どの窓口で・入力と出力・入力ルール・エラー」を一覧にします。今回: ログイン済み本人が PATCH /users/me で { "phone": "09012345678" } を送ると更新後プロフィールが返る。phone は10〜11桁の数字。不正なら400、未ログインなら401。

PATCH と PUT の使い分け

更新系メソッドのうち、PATCH は一部のフィールドだけの更新、PUT はリソース全体の置き換え。今回は phone だけ変えるので PATCH。この HTTP の慣習に沿うと、API の利用者が仕様を推測しやすくなります。

2

設計 — 触る層を確定する

5-1 のチェックリストに当てると、今回は「新しいデータを保存する」ので全層 + マイグレーション + テスト。ここで地図を描いておけば、あとは順に埋めるだけです。

3

DBschema.prisma を編集 → マイグレーション

このコマンド1つで「変更 SQL の生成 → DB へ適用 → Prisma Client の型再生成」まで完了します。? を忘れると既存行に値が無くてマイグレーションが失敗するので注意。

4

REPOSITORYDB 操作を1つ足す

Repository には判断を書かない(第4章)。既存関数の書式をそのまま真似ればOK。

5

SERVICEZod スキーマ + ロジック

入力ルール(10〜11桁)はアプリ固有のビジネスルールなので Service に置きます。戻り値は必要なフィールドだけ詰め直す(password 等を漏らさない)。

6

CONTROLLER+ROUTE窓口を開ける

userRoutes は冒頭で auth を通しているので、この窓口も自動的に認証必須になります。createRoute を書いた時点で /reference の仕様書にも自動反映(手作業ゼロ)。

7

テストを書く → 動作確認

カバーすべき最低ライン: 正常系 / 形式不正(400) / ユーザー不在(404)。npm test が全部通ったら、実際に動かして curl で確認します。

8

整える — lint / format / 型チェック

コミット前の身だしなみ。書き方のばらつきをツールで機械的に揃えることで、レビューが本質に集中できます。

9

コミット & PR

コミットメッセージは feat:(新機能)/ fix:(修正)/ refactor:(内部改善)/ test: / docs: の接頭辞を付ける慣習(Conventional Commits)。PR は「電話番号の追加」のような意味のある最小単位で出すとレビューが速く安全です。
